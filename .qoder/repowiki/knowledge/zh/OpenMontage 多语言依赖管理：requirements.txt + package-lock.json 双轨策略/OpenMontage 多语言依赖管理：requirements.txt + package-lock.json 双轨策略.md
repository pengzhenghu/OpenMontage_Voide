## 1. 使用的系统与工具

本仓库采用**双语言、分层式**的依赖管理方案：

- **Python 侧**：使用 `pip` + `requirements.txt` 声明式依赖清单，配合 `setup.py`（setuptools）进行包分发；通过 `Makefile` 统一封装虚拟环境创建与安装流程。
- **Node.js 侧**：仅 `remotion-composer/` 子模块使用 npm，以 `package.json` + `package-lock.json`（lockfileVersion 3）锁定依赖树。
- **可选 GPU 依赖**：通过独立的 `requirements-gpu.txt` 按需叠加 PyTorch 生态。
- **外部运行时**：通过 `make setup` 中的 `npx --yes hyperframes` 在首次渲染时拉取 HyperFrames CLI，属于“冷启动缓存预热”模式，非严格锁定。

未发现 Poetry、Pipenv、uv pip 等替代工具用于生产依赖解析；`Makefile` 中 `ensure-venv` 会优先检测系统是否已安装 `uv`，若存在则用 `uv venv` 创建虚拟环境，但依赖解析仍走 `pip install -r requirements*.txt`。

## 2. 关键文件

| 文件 | 作用 |
|---|---|
| `requirements.txt` | 核心 Python 运行时依赖（pyyaml、pydantic、jsonschema、openai、fastapi 等） |
| `requirements-dev.txt` | 开发依赖，通过 `-r requirements.txt` 包含核心依赖并追加 pytest、httpx |
| `requirements-gpu.txt` | GPU 可选依赖（torch、torchaudio、torchvision），需额外安装 |
| `setup.py` | setuptools 元数据与 `install_requires`，与 `requirements.txt` 部分重复声明 |
| `Makefile` | 统一入口：创建 `.venv`、安装三类 requirements、运行 Remotion composer、预热 HyperFrames npx 缓存 |
| `remotion-composer/package.json` | Remotion 视频合成器的前端依赖（react、remotion、d3-geo 等） |
| `remotion-composer/package-lock.json` | npm lockfile v3，锁定所有子依赖版本与 sha512 integrity |
| `.python-version` | 指定项目所需 Python 版本（由 Makefile 校验） |
| `.env.example` / `.env` | 第三方 API Key 配置（非代码依赖，但为运行时依赖） |

## 3. 架构与约定

### 3.1 Python 依赖分层
- **核心依赖**（`requirements.txt`）：定义平台可运行的最小集合，被 `setup.py` 的 `install_requires` 镜像一份，保证 `pip install .` 也能工作。
- **开发依赖**（`requirements-dev.txt`）：通过 `-r requirements.txt` 引用核心依赖，再追加测试与 HTTP 客户端库，避免重复声明。
- **GPU 依赖**（`requirements-gpu.txt`）：独立文件，仅在具备 NVIDIA GPU 时通过 `make install-gpu` 安装，同时额外安装 `diffusers transformers accelerate`。
- **版本约束风格**：全部使用 `>=X.Y` 宽松下限约束（如 `pyyaml>=6.0`、`numpy>=1.24`、`openai>=2.44.0`），**未使用 `==` 或 `~=` 精确锁定**，因此 Python 侧无类似 `requirements.lock` 的锁文件。

### 3.2 Node.js 依赖锁定
- 仅 `remotion-composer/` 子目录维护 `package.json` 与 `package-lock.json`。
- 使用 `^` 范围运算符（如 `^4.0.484`），并通过 lockfile v3 锁定具体解析版本与 sha512 integrity hash。
- 通过 `overrides.nanoid = "3.3.18"` 强制覆盖传递依赖的安全漏洞版本。
- 构建脚本通过 `npx remotion studio` / `npx remotion render` 直接调用，无需全局安装。

### 3.3 虚拟环境与安装流程
`Makefile` 的 `ensure-venv` 目标实现以下逻辑：
1. 优先复用已激活的 `VIRTUAL_ENV` 或 `CONDA_PREFIX`；
2. 其次查找本地 `.venv`；
3. 若检测到 `uv` 可用，则用 `uv venv --python 3.10` 创建；
4. 否则回退到 `python -m venv`；
5. 强制校验 Python 版本 ≥ 3.10。

安装命令：
- `make setup`：安装核心依赖 → 进入 `remotion-composer` 执行 `npm install` → 尝试安装 piper-tts → 预热 HyperFrames npx 缓存 → 复制 `.env.example` 到 `.env`。
- `make install`：仅安装 `requirements.txt`。
- `make install-dev`：安装开发依赖。
- `make install-gpu`：安装 GPU 依赖并追加 diffusers/transformers/accelerate。

### 3.4 外部运行时（HyperFrames）
HyperFrames 不是通过 pip 安装的 Python 包，而是通过 `npx --yes hyperframes` 按需拉取的 npm 包。`Makefile` 在 `setup` 和 `hyperframes-warm` 中分别执行一次拉取与刷新，属于“懒加载 + 缓存预热”模式，不纳入版本锁定。

## 4. 约定与约束

- **Python 版本要求**：`setup.py` 中 `python_requires=">=3.10"`，`Makefile` 默认 `PYTHON_VERSION=3.10`，并在 `ensure-venv` 中强制校验当前解释器版本。
- **依赖来源**：全部来自 PyPI 官方源与 npmjs.org 官方源，未发现私有 registry、`PIP_INDEX_URL`、`.npmrc` 或 `pip.conf` 配置。
- **无 vendoring**：未使用 `pip install --no-index --find-links` 或 `npm ci --offline` 等离线安装方式；依赖均在线解析。
- **安全修复**：通过 `package.json` 的 `overrides.nanoid` 显式覆盖已知漏洞版本，体现对安全补丁的主动管控。
- **可选能力隔离**：GPU 相关依赖（torch 系列）与核心依赖分离，避免在无 GPU 环境中引入不必要的重型依赖。
- **API Key 与代码解耦**：第三方服务凭据通过 `.env` 注入（`python-dotenv` 读取），不在代码或依赖清单中硬编码。
- **测试网络隔离**：测试套件通过 socket 拦截禁止访问真实网络，确保依赖行为可确定性验证（见 `tests/test_network_guard.py`）。

## 5. 总结

OpenMontage 的依赖管理遵循“简单、分层、可组合”的原则：Python 侧使用最基础的 `requirements.txt` + `setup.py` 组合，通过 `Makefile` 统一入口管理虚拟环境与安装顺序；Node.js 侧仅在 Remotion 子模块启用完整的 npm 锁定机制；GPU 依赖通过独立文件按需叠加；外部运行时（HyperFrames）通过 npx 懒加载。该方案易于理解与维护，适合中小型多语言工程，但在 Python 侧缺乏 lockfile 导致构建可复现性弱于 npm 侧。
